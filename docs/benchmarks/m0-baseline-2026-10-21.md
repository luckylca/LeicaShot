# M0 image I/O baseline

## Scope

This measures the model-free decode, EXIF orientation, and PNG encode path. It does **not** run color inference, depth, bokeh, SAM, ViTMatte, or GAIC. It is an I/O and measurement baseline, not evidence that the complete Laika pipeline meets a memory target.

The input is deterministic synthetic RGB noise, not a photograph. No user image or model file was used.

## Reproduction

Install the development package, then create the input and run three independent worker processes:

```bash
python -m pip install -e ".[dev]"
python - <<'PY'
import random
from PIL import Image

width, height = 2048, 1536
pixels = random.Random(20261021).randbytes(width * height * 3)
Image.frombytes("RGB", (width, height), pixels).save(
    "/tmp/laika-baseline-2048x1536.png", format="PNG", compress_level=1
)
PY
for run in 1 2 3; do
  laika-bench /tmp/laika-baseline-2048x1536.png \
    "/tmp/laika-baseline-output-${run}.png" --sample-interval-ms 5
done
```

Input SHA-256: `d00162bc745ae24b83eb459743454c6d5abb63e9c11c2808e9e2d3010fb5de3d`.

## Machine and measurement method

- MacBook Air `MacBookAir10,1`, Apple M1, 8 GiB RAM, arm64, 8 logical/physical CPU cores.
- macOS 15.7.7; Python 3.11.16; Pillow 13.0.0; psutil 7.2.2.
- One worker process; no ONNX Runtime, model, or configured inference threads.
- `laika-bench` launches the CLI in a child process and samples process-tree RSS, USS (when accessible), and CPU time every 5 ms. RSS is the primary memory value. USS was unavailable for the child processes on this host. No Linux cgroup exists on macOS, so cgroup and system-wide peak memory were not measured.
- The three runs were performed while host available memory was approximately 1.2 GiB. Treat times as a measurement on a memory-pressured machine, not an idle-device guarantee.

## Results

| Metric | Median | Range | Notes |
|---|---:|---:|---|
| Worker process-tree peak RSS | 34.94 MiB | 34.88–35.06 MiB | 1 sampled process; 5 ms interval |
| Worker process-tree CPU time | 0.272 s | 0.268–0.272 s | Sampled cumulative user + system time; includes interpreter startup |
| Worker wall time | 0.286 s | 0.280–0.286 s | Includes CLI startup and memory sampling |
| Engine `total_seconds` | 0.241 s | 0.240–0.241 s | Measured inside `process_image` |
| Validation stage | 6.31 ms | 5.99–6.41 ms | File, format, animation, and pixel-limit checks |
| Decode stage | 43.91 ms | 42.97–44.75 ms | Full 2048×1536 raster decode |
| Orientation/normalization | 0.035 ms | 0.020–0.046 ms | Already RGB with no EXIF rotation |
| PNG encode stage | 190.40 ms | 188.07–191.21 ms | Lossless PNG at the original pixel dimensions |

The input is 2048×1536 RGB, 9,957,754 bytes. Output is 2048×1536 RGB PNG, 9,452,188 bytes. A pixel-difference check found identical decoded RGB samples and unchanged dimensions. This proves only the model-free baseline's output invariant.

## Limits and next comparison

The RSS result includes Python and Pillow runtime overhead but no learned model. The sampler can miss short-lived allocations, USS was unavailable, and process RSS is not system-wide memory use. The data therefore cannot be compared directly to a cgroup limit or to future ONNX worker peaks without rerunning the same harness on Linux and adding the model-enabled pipeline. Next, record per-stage and complete-pipeline baselines on a fixed real-photo set and under Linux cgroup v2 memory limits before any model optimization.
